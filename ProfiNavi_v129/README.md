# ProfiNavi v138 — regression candidate

Финальный регрессионный проход основного функционала ProfiNavi после v137.

## Ключевые исправления v138

- безопасный startup `client.html` при уже существующих записях;
- сохранение полного booking-flow через login/registration;
- booking привязан к реальному `service_id`;
- корректная длительность услуги и `ends_at`;
- клиент может отменить запись, мастер — подтвердить, отклонить и завершить;
- клиентские и мастерские чаты восстанавливаются из Supabase на другом устройстве;
- frontend закрывает чат после `cancelled/declined` и после 72 часов;
- избранное мастеров синхронизируется с аккаунтом;
- рейтинг/отзывы не падают при асинхронной загрузке каталога;
- мастерские слоты при гидратации учитывают только `is_available=true`;
- `availability_slots.ends_at` создаётся по реальному шагу расписания, а не всегда +60 минут;
- booking-календарь проверяет, что вся длительность услуги покрыта непрерывными свободными окнами;
- локальная проверка пересечений использует диапазон `[starts_at, ends_at)`, а не только одинаковое время старта;
- карта: работает фильтр «На этой неделе», цена проверяется по всем услугам мастера;
- безопасные return-path после login/support — внешние redirect URL отклоняются;
- admin login больше не создаёт неизвестные Auth-аккаунты;
- дополнительное экранирование пользовательских полей публичного профиля;
- удалено неработающее поле «Комментарий мастеру» до появления серверного поля для него;
- устранён лишний закрывающий HTML-тег в карточке мастера.

## Backend hardening

Файл `profinavi_v138_overlap_chat_hardening.sql` содержит серверную защиту от пересекающихся записей для услуг длиннее шага календаря и серверное закрытие conversation после отмены/отклонения booking.

Он должен быть применён к Supabase-проекту ProfiNavi вместе с этой версией. Frontend-проверка нужна для UX, но окончательная защита от race condition должна находиться в PostgreSQL.

## Тесты

В регрессионный набор входят:

- синтаксис всех JS;
- синтаксис inline JavaScript во всех HTML;
- проверка локальных `src/href`;
- проверка дублирующихся HTML id;
- HTTP smoke всех основных экранов;
- unit-проверка duration parser (`90 мин`, `1,5 часа`, `01:30`, `2 ч 15 мин`);
- unit-проверка schedule step и slot intervals;
- 90-минутная услуга на сетке 30 минут;
- отказ при разрыве доступности внутри длительной услуги;
- отказ при локальном пересечении booking;
- safe-return URL;
- admin login без auto-create.

`PN_TEST_MODE=true`, тестовый OTP: `111111`. Перед production необходимо подключить SMS provider и отключить test mode.
